# 需求文档：立案庭分流升级——任务类型×模型候选池路由（v5 定稿：项目决策人拍板选项 A——同厂限制保留，候选池预筛异厂；价格核验专项启动）

> 承办：一审承办 | 2026-09-03 | 立案庭自路由：domain=framework_change → **组合 B（二审承办起步）**
> 决策摘要头：**需求** = 立案庭从"按重要性分流"升级为"重要性 + 任务类型"双维；每个审级席位从单模型变候选池（多替代），按任务类型选最适模型，仍按价格序排列；**方案** = 任务类型分类体系 + 模型候选池（厂商盘点+测评引入）+ 类型×席位路由表；**风险** = 测评成本与引入周期 + 候选模型能力未验证即入池 + 同厂限制在类型维度复杂化。

## 一、需求来源（决策人原话全量，2026-09-03，逐字保留红线 11）

1. 「关于立案庭分流。我在想，关于承办和审级的选择，是否可以再制定更加灵活的策略？现在是根据任务的重要性来对吧？是否能够根据任务的性质来？我理解至少这么几类任务：文本类（还可以包括文本理解类、文本生成类、文本校对类）、代码类（代码生成类、代码审计类）、设计类（UI设计类、3D设计类、图片理解类、图片生成类、动效设计类）等等等等。特别多。」
2. 「是否能够再制定一个根据任务类型进行模型选择的规则？关于模型的话，可以不局限于现在写的9个模型，还可以在已有厂商（现在基本已经有了主流大厂商了）基础上，寻找、测评他们其他的模型有么有更加适合不同任务的模型。」
3. 「然后还是根据模型的价格进行三审的排列。相当于在三审的基础上，每个位置有多个替代模型，每个模型又可以分别承担不同类别的任务。」

## 二、现状（实证）

- 立案庭路由（v3.4.0）：按 domain（强制域）/scale/type-bugfix/history → 组合 A/B/A_exception/C_trigger——**维度 = 重要性与风险，非任务性质**；type 字段仅 bugfix/feature 粗分；
- 九席 = 一席一模型固定（l1_lead=DS flash 等），无候选池；模型选择与任务类型无关（读图/视频虽有 tool_seats 但审级席无类型感知）；
- 已接入厂商：DeepSeek/智谱 GLM/字节豆包/Moonshot Kimi/阿里 Qwen/MiniMax/腾讯混元/火山方舟（生图）——主流全覆盖，**候选池原材料已具备**（各厂商多有同系多型号）。

## 六、分歧节

1. **类型粒度（v2 终态，doubao 裁决）**：12-15 二级类 + 复合兜底；**核心 8 类优先全量落地**（文本生成/文本理解/代码生成/代码审计/UI 设计/图片理解/图片生成/数据分析），长尾按需扩展——控初期测评成本；
2. **承办席分型（v2 终态，doubao 裁决）**：**1 主 2 备**——通用主模型（当前 DS flash）+ 代码专项/长文专项两候选；会话首次触发类型信号时切换，不打断连续工作；
3. **测评节奏（v2 终态，doubao 裁决）**：按需引入 + **月度补测**；核心 8 类首版先全量测评（提速落地）；预算 ≤¥80 上限；
4. **同厂限制在类型维度**：同审级异厂硬约束在候选池下是否仍逐调用校验？（池内候选多来自异厂，同厂同席仍禁）——倾向：规则不变（同审级调用时承办/对抗异厂），池化不破坏该约束；请裁决。

## 七、验收（A-V）

- A1：Taxonomy + 候选池 + 路由表 yaml 落位（机制仓）；A2：30 类型样例路由回测命中率 ≥90%；A3：新候选引入有测评记录且走审计；A4：价格序自检通过；A5：类型路由落地后审级调用质量分不降（月度对账）；D：全程落账。

## 七·五 价格核验专项（v5，决策人红线 5 强化——交叉真实点击审计确认）

候选池初案全部候选型号与价格：真实抓取各厂商官方定价页（WebFetch + URL 落盘证据），双源交叉（官方页 + 第三方检索），**核验结果交对抗席审计确认后**方可入候选池表；证据落 `docs/evidence/候选池价格核验-*.md`；未核验型号一律标注"待核验"，禁止写死价格入池（历史教训：混元免费误称/GLM 缓存价 0.5 错误/E0 算术——PM-3 固化）。
