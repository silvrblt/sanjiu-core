# 三审九方 —— 多模型对抗式审计流水线

> 交互式机制图：克隆后浏览器打开 `docs/mechanism-v4/三审九方机制图-v4.html`（深/浅主题 + 四个视图）

## 缘起

围绕起诉、辩护、审判展开的司法程序，是人类文明为了抑制个体偏见与臆断、在效率与真相之间取得平衡的伟大创造。既然司法程序在人类社会中带来了如此广泛的益处，那么对于诞生于人类自然语言文明的人工智能协作，它同样可能发挥有效的作用。为此，我们参考司法程序的现实运作方式，提出了「三审九方」多智能体治理架构——需要说明的是，三审九方并非对司法程序的逐角色模仿，而是借鉴其核心理念：以对抗与裁决的程序约束，抑制单一主体在认知上的偏见与臆断。在设计上，它与学术界、业界热议的多智能体辩论（multi-agent debate）、反思—修正（self-refine）等思路彼此印证，可以视为对这类协同模式的一种工程化实践，并在我们自己的项目开发中持续落地。因此，我们尝试将其整理并公开，希望帮助更多朋友更好地使用 AI，也诚恳期待大家的批评与建议，一起探索更好的智能体协作架构。

## 一句话定位

单一模型直接产出存在三大系统性缺陷：**幻觉**（编造事实与路径）、**自证**（自己审自己必然放行）、**庸俗一致**（多轮迭代收敛到同一个错误）。三审九方用 **9 个异构模型席位**组成三级对抗流水线——任何任务先经立案庭自动路由，再走「承办 → 对抗审计 → 裁决 → 上诉 → 人工终审」闭环，**禁止单一模型直接输出**。

## 九方矩阵

三审级 × 三角色（承办 / 对抗审计 / 裁决）：

| 审级 | 承办 | 对抗审计 | 裁决 |
|---|---|---|---|
| 一审·基础层 | DeepSeek V4 Flash | 混元 Hy3 | MiniMax M3 |
| 二审·升级层 | 豆包 2.1 Turbo | DeepSeek V4 Pro | Kimi K2.7 Code |
| 三审·终审层 | GLM-5.3 | Qwen3.8 Max | Kimi K3 |

席位排序原则：**输入价格升序**（贵模型放低频审级，控制运营成本）；同审级内同厂互斥；承办与对抗必须异模型（杜绝自审自纠）。

## 处理流程

1. **立案庭自动路由**：任务进入即建卡，一次调用判定审级组合 + 任务类型 + 承办模型；
2. **立案庭三选一**：普通问答 → 当前模型直接回答（不调用审计链）／模式 A（一审+二审，常规任务）／模式 B（二审+三审，对外交付/资金/法律/安全等强制域）；分级路由在保证质量的前提下压缩成本；
3. **审计链（修订版方案制）**：承办出方案 → 对抗审计持全部原始指令输出**修改版方案**（修订版全文+差异索引）→ 承办逐条表态，无异议即敲定落地，有异议交**同一审级裁决一次敲定** → 敲定方案返还双方、交回最初承办方执行；不服则上诉下一审级（仅带背景+异议问题），上诉级裁决为最终意见；
4. **收口门禁**：结项复盘 → 错误模式提报 → 全部拍板落决策台账 → 开工校验记录核验，四件套齐备才可进入完成态。

## 硬红线（摘选）

- 禁止单一模型直接输出；禁止自我校验代替外部审计；
- 审计必须携带完整材料（含原始需求全文），禁止只审摘要；
- 页面类交付必须「截图 + 机械像素丈量」双证据验收，禁止"代码存在即满足"；
- 审计对象必须与交付物一致（SHA-256 冻结锚定，审计后改动须重新送审）；
- 决策与成本逐笔落账、只追加、可回溯。

## 支撑体系

- **机制层**：三审九方规范全文 + 编号机制文件（标准需求处理动作 / E2E 验收 / 可运行性闸门 / 输出治理与复盘）+ 机制包 00–22（审计验收、评价评分、模型调整、报告格式等专项）；
- **配置层**：`sanjiu-models.yaml` 九席模型/价格/调度唯一事实源 + 错误模式库（生产事故复盘沉淀，审计调用自动注入高频错误模式）；
- **工具层**：bridge_core 多厂商统一桥接（输出约束 / 失败分类 / 429 退避 / 预算硬顶）+ 长任务调度执行器 + 开工一致性自检脚本；
- **视觉三席**：读图 / 生图 / 视频理解为独立工具席，只采集证据、不参与裁决。

## 实证

- 两批 6 任务类型 × 8 席模型类型测评回填，席位分配由实测达标度驱动；
- 承办席经全面盲测终审回切（三证合一：评分、领域实测、成本）；
- 20 条人工纠正红线全部来自真实生产事故复盘（含验证设计退化、审计后漂移、静默失败配置等类别）。
