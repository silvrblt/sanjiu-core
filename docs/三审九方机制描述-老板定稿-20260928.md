## 一、老板原话全文（定稿依据）

「在立案庭路由以后，就没有什么承办路由了，立案庭之后，就是三个选择：
（1）针对普通的问答类问题，不调用三审九方，直接由当前的模型进行回答；
否则，（2）进入模式A（一审+二审），先转一审承办，进入一审程序；
（3）进入模式B（二审+三审），先转二审承办，进入二审程序。
每一审的承办都需要分析需求、出方案，然后每一审的审计都需要在获取任务下达的全部指令的情况下，对承办的处理结果提出对抗审计的意见。然后按照结构化的语言方式，把内容返还给承办。承办还有异议的话，就按照用户原话、承办分析、审计意见、需要裁决的问题这样的格式，传递给同一审级裁决模型。裁决处理以后，把裁决的处理意见分别返还给承办和审计模型。承办和审计有任何意见的，就上诉给下一审级的承办模型，上诉的内容就单纯是介绍问题背景、需要上诉处理的异议问题，下一审级的承办模型进行分析，给到审计模型，还是审计模型反馈，承办模型不同意的，给到裁决模型进行裁决。这一次裁决意见为最终意见。如果是涉及到影响到最终商业决策的，就在裁决模型整理好问题后，给到用户进行最终判断。」

「（1）承办和审计之间不能来回扯皮，审计意见只要承办有不同意的部分，直接转裁决。对于裁决意见，承办和审计有任何一方有不同意的内容，针对不同意的内容就可以上诉到下一级审级；
（2）特别要注意，在审判信息传递的过程中上下文是在不断压缩的，最终是针对背景信息下的存在争议的问题进行裁决，而不是重新发表全套的意见。
（3）每个承办、审计、裁决，都有一套验收的纪律需要遵守，这个应该也是确认过的之前，检查一下还在不在，主要是需求满足、代码纪律等等
（4）贯穿在这些流转的过程中，我们还嵌入了很多的技能进去。比如ponytail、code-review、requirement-analysis等等」

## 二、流转总图（定稿版）

1. **立案庭路由 = 三选一判决**（此后无"承办路由"环节）：
   - ① 普通问答 → 不调用三审九方，当前模型直接回答；
   - ② 模式 A（一审+二审）→ 转一审承办，进入一审程序；
   - ③ 模式 B（二审+三审）→ 转二审承办，进入二审程序。
2. **每审级内流转**：承办分析需求、出方案 → 审计（持任务下达的全部指令）提对抗审计意见，按结构化语言返还承办 → 承办有异议 → 按【用户原话、承办分析、审计意见、需要裁决的问题】格式交同审级裁决 → 裁决意见分别返还承办与审计。
3. **上诉**：承办或审计对裁决有任何异议 → 上诉下一审级承办；上诉内容 = 问题背景 + 需要上诉处理的异议问题（纯争议问题，不重发全套意见）→ 上诉级承办分析出方案 → 上诉级审计反馈 → 承办仍不同意 → 上诉级裁决 = **最终意见**。
   - 模式 A 的上诉级 = 二审；模式 B 的上诉级 = 三审。
4. **用户终判**：涉及最终商业决策 → 裁决模型整理好问题 → 用户最终判断。
5. **防扯皮硬规则**：承办与审计不来回拉扯——审计意见承办有不同意部分即转裁决；裁决意见任一方有异议即上诉（仅异议部分）。

## 四、纪律失灵根因与固化分析（2026-09-28）

**根因三断点**：
1. 路由失灵 = 约定非闸门（lead_route 靠会话自觉调用；ZCode hooks 源码级确认可注入回执但不可自动换模型）；
2. 十几轮扯皮 = 流转无硬状态机（无轮次上限、无"异议必转裁决"强制——实证 08-26 一审对抗 9 轮）；
3. 审查纪律不遵守 = 纪律在文档里、审计模型看不见；桥接已做部分工具层强制（S8 注入/错误模式 top5/输出约束），承办侧与格式侧仍靠自觉。

**固化三选项**：
- 纯 skill（skill-creator 产出）：操作手册+状态机提示+格式模板；soft 约束，模型可绕过，解决不了路由失灵；
- 插件/hooks：可注入上下文、PreToolUse 拦工具调用；**不能换模型、不能拦内容**（09-23 源码定论）；
- 工具层状态机（推荐核心）：三选一判决 + 流转状态机（每级 对抗≤1 轮、裁决≤1 轮、上诉仅 1 次、材料字段 schema 强制：用户原话/承办分析/审计意见/待裁决问题；上诉包强制：背景+异议，禁全套）+ 轮次硬上限，写在代码里，模型只能经工具流转（同 bridge_core Q-EX0 硬编码思路）。

**推荐组合**：C（工具层状态机做硬约束）+ skill-creator 产出一个「三审九方流转手册」skill（三选一卡、每步传什么/格式模板、验收纪律速查、防扯皮规则）随任务强制加载 + hooks 注入回执（可选）。待老板拍板后走正式审计立项。
