# 需求文档：三审九方审级组合化 + 立案庭智能分流（v2，Hy3 一审 7 项全接受）

> 承办：一审承办 | 2026-09-03 | 状态：待审（需求分析 = 奠基文件，走二审闭环）
> 决策摘要头：**需求** = 审级组合化（不再每次走全链），难任务二审起步、简单任务二审封顶，前端"立案庭"按规则智能分流；说"三审九方"即自动组合路由；**方案** = 三种组合定义 + 立案庭规则表（任务特征×审级特征匹配）+ skill/脚本固化；**风险** = 组合化可能削弱质量保障（强制域清单（5 项：对外交付/资金/法律/安全/框架）兜底必须保留）+ 规则误分流。

## 一、需求来源（老板原话全量，2026-09-03，逐字保留红线 11）

1. 「关于三审九方，我认为可以进一步做一个组合式的归类。第一类：一审+二审；第二类：二审+三审；第三类：一审+三审（可以判断这一类要不要，有没有必要）。这样的话，就不要没事走三个层级了，避免重复的浪费，实际上难任务就应该一开始就二审起步，然后还有，简单任务就应该二审封顶。」
2. 「然后再做一个前端立案庭。立案庭预先设置一些规则，对接收到的任务，进行智能的分流，不同组合的审级存在哪些区别？到底应该走哪个审级组合？怎么样符合任务的特点和审级的特点？思考这个规则怎么建立，上面的审级分流组合怎么搭建。」
3. 「然后可以尝试固化一下，不论是走/skill-creator还是固化脚本，等等方式。这样实现，我只要说三审九方，就可以进行智能的组合选择这样」

## 二、现状与问题（实证）

- 现状机制：一审全量 → 二审介入 ≥70% → 三审按需（强制域清单（5 项：对外交付/资金/法律/安全/框架）全链）——**大量常规任务实际走了 1-2 轮**，但审级边界模糊（二审 70% 介入 + 随机抽审），难任务也常从一审走起（成本浪费 + 时间延迟）；
- 本次 cost-opt 实测链（两窗口日 ¥4+）：承办产出 → Hy3 → M3 → DS Pro×2 → GLM → Qwen×2——共 7 轮审计（含退回），部分轮次属"一审就能拦截但二审才抓出"（附录 A 转录失真 = 清单可查类，一审放行）；
- 强制三审清单（对外交付/资金/法律/安全/框架）必须 100% 保障——组合化不得击穿。

## 四、技术路径（含三组合 vs 现状对比）

### 4.1 组合语义（详细）

| 组合 | 流程 | 适用（初步信号） | 成本系数 | 时长 |
|---|---|---|---|---|
| A 一审+二审（二审封顶） | 一审承办 → 一审对抗 Hy3 →（分歧 M3）→ 二审对抗 DS Pro 终核 | 常规开发/文档/内部工具；无强制触发；复杂度中低 | 1.0（基准） | ~1 轮次日 |
| B 二审+三审（难任务起步） | **二审承办（l2_lead，doubao-2.1-turbo，九席既有席位）起步** → 二审对抗 DS Pro →（分歧 K2.7）→ 三审对抗 Qwen 终核 →（分歧 K3） | 强制域清单（5 项：对外交付/资金/法律/安全/框架）；跨模块重构；金额/合规/安全；外部交付 | 2.2（较全链省一审轮） | 同全链但少 1-2 轮 |

### 4.2 立案庭规则表（v0 草案，R2 回测后调参）

```yaml
routing_rules:
  # 判定顺序（v2 分层，P3）：① domain 强制信号（最高优先）→ ② scale/type → ③ history 仅辅助加权（新域无历史不得判低风险）
  force_b:
    # 强制 B 类清单（v4 显式定义，M3 Q6）：五域 + 跨模块重构 + 历史高错误率
    # 判据：域=任务卡 domain 字段；跨模块重构 = 涉及 ≥3 个模块/仓库文件变更 >20 文件
    # history 窗口 = errors-ledger 30 天滚动 count≥5（M3 Q8；新域无历史不判低风险）
    - {domain: external_delivery}
    - {domain: finance}
    - {domain: legal}
    - {domain: security}
    - {domain: framework_change}
    - {scale: cross_module_refactor}
    - {history: error_rate_high_30d_ge5}
  # 简单信号 → 组合 A（可一审即一审；二审封顶防漏）
  simple_a:
    - {scale: single_file}          # 单文件级
    - {type: bugfix}                # bug 修复
    - {type: internal_tool}         # 内部工具
    - {domain: none_above}          # 无强制域
  # 升级触发器 C（非路由目标，仅 A 运行中一审对抗出重大分歧时自动升级）
  trigger_c:
    - {dispute: major_at_l1, l1_kappa_lt: 0.2, l1_block_rate_gt: 0.3, p0_flag: true}
    # 条件（v6 机器可读，与 R1/§八·五 一致）：一审对抗 l1_kappa<0.2 且 l1_block_rate>0.3，或 p0_flag=true → 升三审终核
  # 兜底：无信号匹配 → 组合 A（默认），立案庭留痕可人工改
  default: A
```

### 4.3 立案庭触发与固化形态（分歧 1）

- 形态选项：a) skill「三审九方」扩展（立案庭规则内嵌，说"三审九方 X"即先跑路由）；b) 脚本/router CLI（bridge 层 route 子命令，任务卡带审级字段）；c) a+b 混合（skill 作入口 + 脚本作规则执行）；
- 承办倾向 c：skill 承载"说三审九方即分流"的入口体验，脚本承载规则引擎（可回测、可审计），规则表 yaml 单一事实源；
- 立案庭动作：接收任务 → 提取特征（域/规模/类型/历史）→ 规则匹配 → 输出「审级组合 + 理由」→ 任务卡落审级字段 → 后续审计链按组合执行。
